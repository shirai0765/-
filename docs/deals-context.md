# 営業提案の店舗適性

営業カタログの新しい店舗提案に、提案作成時の店舗規模と決算実績を反映する。12種類の既存提案を使い、種類の追加や経済全体の利益補正は行わない。最初の入門提案2種類、不動産提案、保存済みの旧提案は従来どおり。

## 判断できること

- POS・電力診断・人員支援は、直近決算の1店舗あたり客数が少ないほど効果幅が小さくなる。客数1,000人／週を代理指標の上限とする。待ち行列、欠員、電力使用量を実測したとは説明しない。
- 共同仕入れは店舗数と客数、育成・顧問は店舗数を使う。規模による上限は5店舗。大きくなるだけで際限なく利益が増えない。
- 会員アプリは対象客数、法人仲介は既存客数の少なさを代理指標にする。再来店率、設備の空き、実際の法人需要は未計測と説明する。
- 決算に現存店舗の結果がない場合は「未観測」。客数0の実績とは区別し、客数要因の効果幅を縮めない。閉店済み店舗の結果は除外する。
- 赤字店舗数も決算から表示するが、赤字そのものへの利益ボーナスはない。

効果幅は旧カタログの25〜100%内に限定し、非負とする。初期支払・週額費・解約費・期間は据置き。営業側の提示額は元の最大事例のままなので、作成時の状況を反映した幅との違いを読める。調査後は同じ幅の中で範囲が狭まるが、結果は導入後まで確定しない。調査しない見送りも可能。

全期間の純収支は `効果×(契約週−導入待ち)−初期支払−週額費×契約週−支払済み調査費＋残価`。満了まで解約しない仮定。残価は現金回収で営業利益ではない。調査後の費用を二重請求せず、比較表示に含めるだけ。

## 保存契約

新しい店舗提案IDは `cafe-{batch}-{category}-fit-v3-{template}-{店舗数}-{観測店舗数}-{観測客数合計}-{損益0以下店舗数}-{決算週}`。作成週は既存の `createdWeek` を使う。店舗数は1〜10,000、客数合計は最大10億人、各数は非負の安全な整数、観測店舗数は店舗数以下、損益0以下店舗数は観測店舗数以下。未観測なら観測数・客数・損益0以下数・決算週はすべて0。決算週は作成週を超えない。

`getCanonicalDealOffer` はIDに固定された情報だけから提案を再構築する。現在の店舗数、価格、決算などでは再計算しない。調査と導入結果の乱数キーから状況部分を除き、同じseed・同じ案件で状況の違いが結果に与える影響を比較できるようにした。旧版の乱数キーは変更しない。

新しい保存フィールド・保存版の変更は不要。既存v1/v2の生成・調査・結果の数式と文面を保つ。新しい案件を実体化した `initializeDeals` の結果を保存すれば、その後の条件変更でも前提は固定される。表示だけでまだ実体化されていない提案は、その時点の状況から決定的に生成する。

保存検証はIDの構文・範囲と正規化された全条件・文面を照合する。IDだけ、効果額だけ、文面だけを書き換えた保存は拒否する。`isDealOfferId` を見送りID検証に使う。ローカル保存の全情報を整合する形で作り直したものの過去の真偽まで証明する仕組みではない。

## 検証

`tests/deals-context.test.ts` は同じseedで客数・店舗数だけを変えた因果比較、未観測と実測0の区別、閉店店舗除外、調査・契約・JSON往復後の固定、旧v2互換、不正ID・数値の拒否、全期間収支を検証する。費用と借入中の利益条件は既存のエンジンを使用する。

保存の限定再レビューでは、配布済み `Shibuya-Capital-0.3.2-source.tar.gz` の実装と旧4形式・v2全10種の調査前後をseed 0/42/4294967295で比較した。84通りの全提案内容と実現効果が一致し、その独立した旧版結果のSHA-256を回帰テストへ固定した。さらに保存エンベロープの往復、新v3の調査→契約→別提案見送り→店舗設定変更→効果判明までの決算・再保存、不正な前提上限・未観測値の矛盾・未知テンプレート・契約IDだけの改変を確認した。営業既存9件＋適性・保存10件が成功。
