# セーブとWindows版 — 0.4.0

アカウント不要のローカル保存。クラウド同期は実装していない。ブラウザのサイトデータ消去、プライベートモード終了、PC故障に備え、重要な節目にJSONを書き出して別の場所にも保管する。

## 保存契約

- 週次進行は `saveGame(next)` の成功後に決算後のUI状態を確定する。連続営業も1週ずつ保存する。保存失敗時に未保存の決算だけを画面へ進めない。一方、開店・調査・契約など計画中の操作はまず画面状態を変え、週末または「今すぐ保存する」で永続化する。
- IndexedDBの単一トランザクションで本体と週次バックアップを更新する。本体とは別に最大12件を保持し、会社IDと週が同じ記録は更新する。この上限は保存領域内のバックアップ全体に適用する。
- 別タブが本体を更新した後は古いリビジョンからの保存を拒否する。最新の保存を読み直す必要がある。localStorageへの自動切替はない。
- JSONは形式識別子、スキーマ1、保存日時、SHA-256チェックサム、ゲームデータのJSON文字列を含む。ゲーム状態の `version` も1のまま。チェックサムは破損検出用で、改造を防ぐ署名ではない。
- 読み込み時は型、有限数値、範囲、重複ID、必要な参照、配列上限を検査する。異なる形式や未対応バージョンは拒否する。元のカードゲームのデータは読み込まない。
- `importGame(file)` は検証済み状態を返す。呼び出し側は `await saveGame(imported)` が成功してから現在の会社を置き換える。`restoreBackup(key)` は検証と保存まで行い、破損した本体からも正常なバックアップを選べる。
- `exportGame(state)` は非同期。呼び出し側でPromiseの失敗を捕捉する。JSON交換にはブラウザ版とWindows版で同じ形式を使う。

実装は[保存処理](../src/persistence.ts)と[画面の保存呼出し](../src/App.tsx)。0.4.0は任意項目の追加と提案IDの版で互換性を保ち、旧データへ過去の記録や企画を補完しない。将来の未対応形式を読み替える移行処理はない。

## 営業提案・契約

`deals` は任意。提案、調査済み状態、見送りID、契約、判明週・終了週、累積費用・効果、解約・終了状態、生成済みバッチ、最後に処理した週を保存する。無印v1とv2の価格・文面・調査結果・実現額は従来の定義から再構築し、現在の事業状態では変えない。不動産カタログと初回入門提案も既存形式を維持する。

0.4.0で新規生成する店舗カタログ提案は、次のv3 IDへ作成時の前提を含める。別の任意contextオブジェクトは追加しない。

```text
cafe-{batch}-{category}-fit-v3-{template}-{stores}-{observedStores}-{customers}-{lossMakingStores}-{reportWeek}
```

`stores` は作成時店舗数。残りは直近決算に含まれる現存店舗の観測店舗数、客数合計、損益0以下の店舗数、決算週。決算に対象店舗がなければ未観測として最後の4値を0にする。実測客数0なら観測店舗数・決算週が残り、未観測と区別できる。後日の開閉店や設定変更、読み込み時の現在値で固定前提を再計算しない。

[提案の正規再構築](../src/sim/deals.ts)と保存検証で、次を照合する。

- v3は既知の店舗向けテンプレートと種類、先頭ゼロのない整数表記、120文字以内のID、最大83,333のバッチ番号を要求する。バッチと作成週も一致させる。
- 店舗数1〜10,000、観測店舗数は店舗数以下、客数合計は最大10億、損益0以下数は観測店舗数以下。すべて非負の安全な整数。未観測時の値の矛盾、観測済みなのに決算週0、作成週より未来の決算を拒否する。
- 初期費用、週額費、期間、調査後の幅・文面などを、保存されたID・シードから再構成した条件と比較する。判明済み実現額も決定的な計算結果と一致させる。IDだけ・金額だけの改変は通らない。
- 契約IDは `contract-{offer.id}`。開始週は提案作成〜有効期限内かつ現在週以下、判明週は開始＋導入待ち、終了週は開始＋契約期間。同じ提案の重複契約や同種の稼働契約重複を拒否する。累積費用・効果には経過週から求める上限がある。
- `deals.offers` に同じIDの元提案がある場合、契約内 `offer` の各保存フィールドと元提案を比較し、不一致を拒否する。元提案行の存在自体をすべての旧契約へ追加要求する仕組みではない。
- 見送りIDも `isDealOfferId` で検査する。v3はテンプレート・固定前提の制約を使い、無印・v2の見送りIDは従来の形式検査を維持する。見送り文字列だけから調査済み内容を作らない。

提案・契約・生成済みバッチ・見送りIDの各配列は最大10,000件。判明前の実現額、期間・種類・累積額の不整合も拒否する。条件や効果を変更する将来版では、既存版の再構築処理を保つ必要がある。チェックサムを更新しても検証に反する契約は取り込めないが、保存全体を整合する形で作り直した場合の過去の真偽を証明する署名・サーバー検証はない。

[営業適性・保存テスト](../tests/deals-context.test.ts)では旧0.3.2アーカイブと84通りの提案内容・実現額が一致し、保存エンベロープも往復する。v3の調査・契約・見送り・設定変更後の決算・再読込と、不正な固定前提の拒否も検査する。画面操作の証跡は[営業DOMプレイテスト](sales-context-playtest.md)。

## 任意の沿線共同企画

`railProjects` は任意項目で、ない旧保存はないまま読み込む。保存するのは計画の選択と時刻だけ。

```ts
railProjects?: {
  projects: {
    districtId: 'center' | 'dogenzaka' | 'miyashita' | 'sakuragaoka';
    choiceId: 'commerce' | 'rental';
    startWeek: number;
    completeWeek: number;
  }[];
}
```

`railProjects` 直下は `projects` のみ、各計画はこの4フィールドのみを許可する。最大4件・同一地区1件、定義済みの二択、着工週1以上かつ現在週以下の整数、完成週が着工週＋所定工期（商業4週／賃貸6週）と一致することを検査する。計画を持つ保存には上場済みを要求する。任意の完成フラグ、利益額、独自の効果率は保存できない。

着工時の信用45以上・対象地区の物件直接保有は[着工操作](../src/sim/railProjects.ts)で検査する。読み込み時に現在の信用や保有を同条件へ戻すことは要求しない。着工後に信用が下がったり地区物件を売ったりした正規の保存を読み込める。

工事中・完成・休止は現在週、固定された完成週、現在の物件保有から派生する。最後の地区物件を売ると効果と維持費は休止し、工期は経過する。再取得時にはその時点の工事中／完成状態で再開する。読込だけで着工費を再請求したり、別の計画を追加したりしない。詳細は[沿線共同開発](rail-projects.md)、保存・週次処理との接続は[統合テスト](../tests/integration-v4.test.ts)を参照。

## 出店記録

0.3.2からの任意項目 `openingRecords` に最近40件の出店時予測と初決算を保存する。520件までの収支履歴とは独立し、41件目以降は古い出店記録を切り詰める。記録機能以前の店の予測・過去実績を後から作らない。初決算前の閉店と、同週・同区画への再出店を区別する。旧形式・端数の現金を含む往復、保存失敗時の再試行、不正値拒否は[出店記録テスト](../tests/opening-journal.test.ts)を参照。

会社IDと週をバックアップキーに使うため、新しいゲームでは異なるシードまたは会社IDを生成する。同一シードを指定するテストは経済計算を再現できるが、同じ会社ID・同じ週のバックアップを別記録にはしない。

## Windowsシェルとパッケージ

[desktop/main.cjs](../desktop/main.cjs) はビルド済み `dist` を専用オリジン `capital://game/` で配信する。Node無効、コンテキスト分離・サンドボックス有効、外部ナビゲーション・新規ウィンドウ・外部通信を拒否する。保存はElectronのユーザーデータ領域内のIndexedDBを使う。Windows独自の別ファイルへの自動バックアップはない。

パッケージ作成は実装済みの次のコマンドを使う。electron-builderの追加設定は不要。

```sh
npm run package:windows
```

これはWebビルド後、[Windowsパッケージスクリプト](../scripts/package-windows.py)で固定バージョンの公式Electronを取得し、公式SHA-256一覧との一致を確認して、アプリとZIPへまとめる。既にビルド済みなら同スクリプトを直接呼べる。パッケージ内にアプリファイルのハッシュ一覧とbuild-infoを保存する。

現在のパッケージスクリプトは `windowsRuntimeTested: false` を記録する。ZIP生成・静的検査と、Windows実機での起動・保存・復元・JSON交換は別の確認。署名のない実行ファイルでOS警告が出る場合がある。保存を維持するため、起動パッケージの識別名と保存オリジンを不用意に変更しない。
