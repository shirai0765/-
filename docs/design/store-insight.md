# 0.4.2 店舗設定の理由が分かる表示 — 設計・受入方針

2026-10-06。設計方針と、実装後の経済一致検証。研究担当が所有し、鉄道経済担当の公開読み取りAPI、資本担当・営業担当の表示案を相互批評した。0.4.1の配布・経済係数・既存QAは変更しない。根拠は[店舗設定の小規模実験](../research/store-strategy-study.md)と[全測定結果](../research/store-strategy-study.json)。世界最適や人間の理解を証明した研究ではない。

**初見の目的は「今の店は何が不足し、設定を変えると今週と先の成長にどう効くかを分かること」。最適設定を自動で教える画面にはしない。** 現状は設定次第で利益が大きく変わるが、価格・人数・品質・広告の数字だけでは、需要が足りないのか、迎える能力が足りないのかを読み取りづらい。

## 先に見せるもの

1. **店名・今週の店舗利益・制約の説明1行。** 「今週、この設定で営業した場合」と示し、「来店の見込みが処理能力を上回っています」「受け入れ枠に余裕があります」のように理由を添える。結果を先に置き、その根拠へ進める。赤字でも満席でも自動的な失敗・成功とは断定しない。
2. **来店需要の見込み → 店の処理能力 → 実際に迎えられる人数。** 3値を上の説明の根拠として一つに束ね、同じ単位・週の予測として並べる。必要な場合だけ取りこぼしまたは余力を短文で添える。「空席」はテイクアウトにも共通する表現ではないため、基本は「処理の余力」と呼ぶ。需要との差を確実に売れたはずの売上へ換算しない。
3. **利益の理由になる費用。** 材料・人件費・家賃・広告・店舗維持・店長費などの内訳は展開できる形にする。同じ店舗利益を何か所にも大きく繰り返さない。赤字や主要な負担は閉じた詳細の外でも分かる。全社純利益・本部費・利息・元本返済と同じ値にはしない。
4. **今週の予想満足度と、信用は営業を重ねて変わる旨。** 高い今週利益と低い満足を同時に読み取れるようにする。信用45へ何週で到達する、IPOが何週早まる、といった将来の保証は出さない。

全要素を新しい長い必読表にまとめない。390pxでは店名・店舗利益・診断が先に読め、その根拠の3人数と満足へ普通の縦スクロールで続ける。細かな係数・乱数・seed・探索候補・式は主画面へ列挙しない。必要なのは「値がどのように選択に関係するか」であり、内部の設定値をすべて公開することではない。

## 値の意味を守る契約

| 値・表現 | 表示上の意味 | 避ける誤解 |
|---|---|---|
| 来店需要 | 今週の価格・品質・広告・周辺条件によるモデル上の見込み | すでに来た実測客数、確実な予約人数、無条件に売れる人数 |
| 処理能力 | 今週の実効人数・形態・設備・運営体制で対応できる上限 | 座席の数そのもの、全員に同じ効果がある採用可能人数 |
| 迎えられる人数 | 需要と能力の小さい側で決まる今週の予想客数 | 取りこぼしも売上へ計上する、広告で必ず増える |
| 店舗利益 | この店の売上から店舗費用を差し引いた額 | 全社純利益、開業費控除後の現金、返済後の残高 |
| 満足 | 今週の実効価格・品質・混雑などから得る予測 | 全社信用への即時加算値、固定の将来売上保証 |
| 創業者の運営能力 | 店長なしの店が増えると低下する処理倍率 | 4店舗以上なら必ず会社全体が赤字、すべての店が同率低下する |
| 店長の調整 | 委任した枠内で今週の営業設定を調整する予測 | 全探索の最適化、必ず増益・満足65以上、元の入力値のまま営業 |

需要・能力には端数がある。診断はエンジンの値に基づき、表示人数の丸めだけで状態を変えない。「見込み1,120人・能力1,120人」なのに「0人を取りこぼす」と強調するなどの矛盾を避け、差が表示精度未満なら「上限付近」などで伝える。APIの丸め方・比較境界は実装側との合意後に検査へ固定する。

品質100について「費用だけ増える」と総効果を断定しない。測定したセンター街標準・950円・4人・広告0円では、品質85→100で来店者は1,120人のまま、利益402,440→383,120円だが、満足79→84へ上がる。適切な説明は「今週の客数は上限のため増えず、材料費は増える。一方、満足は上がる」である。費用と便益の時間軸を分ける。

上の差分説明は同じ週の前後比較を保持した検証例に限る。変更履歴のない通常UIでは「品質を上げたので満足が5増えた」と推定せず、「客数は対応上限に達しています。品質は材料費と予想満足度にも影響します」と現在の予測を示す。品質による需要増が混雑にも影響するため、「品質を上げれば必ず満足が上がる」と一般化しない。

## 具体的な受入ケース

数値は研究seed812の測定例。QAは公開actionで状態を作り、実装の読み取りAPI・`previewWeek`・実週決算を照合する。UIが別のseedを使う場合にこの固定値を強制しない。

店長ケースは今回の数値研究では計測していない。`managerPlan`と週次決算の実装読取に基づく追加の受入対象であり、研究済みの実験結果とは区別する。

| ケース | 操作・条件 | 先に分かるべきこと | 検査すること |
|---|---|---|---|
| 初店の通常設定 | 新会社→center-01標準→設定未変更 | 1,120人を迎え、店舗利益53,528円。需要が処理能力を上回っても現状が即失敗とは限らない | 「今週予測」と表示。店名・客数・店舗利益が公開計算と一致し、初決算の実績を後から書き換えない |
| 処理上限に達する | center-01標準、950円/4人/品質85/広告0 | 需要が増えても処理上限1,120人で止まる。集客だけで今週利益が増えるとは限らない | 能力・客数と診断の整合。人数/設備を変えた後の上限を更新。人員のレベル上限を超える増員で能力が増えないことも説明できる |
| 処理余力がある | sakuragaoka-06標準、1,400円/2人/品質100/広告1万円 | 客数427人に対し能力560人。さらに採用することが集客の代わりにはならない | 133人程度の余力を負の取りこぼしとして扱わない。広告や値下げの効果を保証せず、変更後の需要/費用を再計算 |
| 品質増が今週の客数を増やさない | 上記センター街満席設定で品質85→100 | 材料費増による利益19,320円減と、満足5増を両方見る | 客数1,120人据置・利益402,440→383,120・満足79→84。品質変更の初期課金なしと、材料運転費の増加を区別 |
| 高利益だが低満足 | center-01プレミアム、2,000円/4人/品質100/広告1万円 | 利益918,175円でも満足47。利益の緑だけで全面的成功と読ませない | 低満足が内訳の奥へ隠れない。13週実験の信用15.71は研究結果であり、画面で同じ将来到達を保証しない |
| 4店を自主管理 | 研究のcenter-01/center-04/桜丘/宮下、店長なし | 4店の時点で創業者能力約0.870。対象店の能力が低下し、本部費も別に生じる | 店舗能力と全社費用の区別。3店→4店で全店の入力人数を勝手に減らさない。1店へ店長を置いた場合は残り自主管理店の条件も更新 |
| 店長の自動調整 | 公開updateStoreでmanager=true | 入力値と、今週に店長が実際に選ぶ価格/人数/品質/広告は異なる場合がある | 店長の実効設定から需要・費用・満足を計算し、`previewWeek`と一致。配分枠・実人件費・別の店長費を混ぜない。表示だけで保存値を上書きしない |

店長の配分枠は現行では入力人数×基準人件費＋広告から作る一方、実際の給与には景況の賃金倍率がかかり、店長費も別にある。主画面で内部式を読ませる必要はないが、配分枠を実費の合計と誤表示しない。店長は限られた候補を探索し、元設定を残す場合もあるため、無条件に「必ず最善」「必ず満足65以上」と書かない。

費用内訳は個別項目の円丸めと、計算側の合計後丸めで差が出る可能性がある。店舗利益の正本はエンジンと一致させ、内訳の丸め差を無言で別の費用に見せない。APIと表示で契約を定めてから、端数を含む週の検査を追加する。

自社物件の店舗は家賃0でも、物件の維持費が全社側に残る。「場所にかかる費用なし」とは説明せず、逆に全社側の物件費を店舗内訳へ足し直して店舗利益と不一致にもさせない。信用の週末更新は全店満足の単純平均と全社利益の正負などに基づくため、客数で加重した平均や、その一店だけの満足を信用増加量として表示しない。現在の信用との関係もあり、単店満足が高くても信用上昇は保証できない。

また全社の創業者能力が低下していても、店長を置いた店は別の能力倍率で計算される。選択中の店に適用されない「自主管理で能力が低下」という警告を出さない。

## 変更前後の見せ方と安全な操作

今回の初期scopeでは、入力変更後の今週予測を正しく読むことを優先する。以前の設定との比較を追加する場合は、比較基準を「変更前の同じ週」に固定し、異なる週の景況・信用・他店の変化を混ぜて設定の因果効果と断言しない。

店舗選択、内訳の開閉、表示品質変更だけでは営業週・現金・品質設定・店長の入力枠を変更しない。実際の入力変更には既存actionを使い、専用の隠れた経済stateを作らない。既存の借入利益0以下・週末現金不足の全社警告は、この店舗カードの高利益表示で置き換えたり隠したりしない。

数値は色だけで区別せず、赤字/予測/実績/満足/上限の文字を添える。入力値が消える、別店舗の説明が残る、未選択・閉店済みの店に古い指標が出る、といった状態遷移も受入対象にする。

## 相互批評と検証の区分

API担当へ、店長の実効設定、端数の境界、配分枠と実費の違いを先に伝えた。資本担当と営業担当へは「需要・能力・来店の3値から始め、費用と信用の異なる時間軸へ進む」順序と、不要な内部係数を主役にしない案を依頼した。

営業担当は7ケースに賛成し、「前後比較を保持しないUIで品質変更の差分を断言しない」「品質向上を無条件の満足上昇と表現しない」と指摘した。このため現在の予測説明と、同週の比較結果を上記で分けた。店長については「今週の店長案」に実効価格/人数/品質/広告を出し、入力値を消さず、配分枠と実費の違いは詳細で説明する案に合意した。

資本担当は、需要3値から始めると新たな数字一覧になり得るため、「今週の店舗利益＋制約1行」を先頭に、その根拠として3値を束ねるよう提案した。採用し、上の順序を修正した。「客が足りない」は黒字の店でも失敗と読まれやすいため「受け入れ枠に余裕」を使う。取りこぼしを確実な売上としないこと、店長費の二重控除を避けること、満足から信用への更新は全店舗集計と全社利益を通じることも合意した。実在企業IRは費用や主体の区別には役立つが、本作の品質値や需要係数を直接校正する根拠としては不足する。

追加のエンジン読取批評では、自用物件の家賃0と全社物件費、信用の単純平均、店長の元設定保持を確認した。上の意味の境界へ反映し、「自用物件は費用ゼロ」「店長なら常に満足65以上」といった説明を受入不可とした。

API担当の案は`getStoreOperatingInsight(state, id)`で、入力設定・店長の実効設定、需要/能力/客数/未対応需要/余力、実店舗結果、費用内訳と円丸め調整、関連する運営条件を別々に返す。存在しない店舗IDはnull、表示だけではstateを変えず、信用の将来値を返さない。この契約で読み取りAPIが実装され、経済・保存結果の独立照合を下記で行った。閉店IDなど個々のAPI境界の単体検査と、ブラウザの表示検証は別の担当証拠を参照する。

実装GO後のDOM検証では実API/エンジン値との一致、状態の無変更、390pxとデスクトップの可読性、明示した7ケースを確認する。CityViewをstubにする場合はその旨を記録し、実レンダリングの証拠と分ける。画面の読みやすさや改善理由を初見ユーザーが理解できるかは、別途「次に何を変えたいか／なぜか」を聞く観察で確かめる。自動テストが通ったことを、人間の理解・面白さ・30時間体験の証明にしない。

## 経済が変わらないことの独立検証

API担当の29ケース比較を読取レビューし、研究担当でも再実行した。基準は `/tmp/store-insight-v041-baseline.json`、旧ソース控えは `/tmp/store-insight-v041-source/src`。控えのengine SHAが基準記録と一致し、旧engineに新APIが存在しないことを確認した。さらに旧engine自身で各基準状態の予測・週進行・店長案・出店見積りを再計算し、基準の内容も一致した。

| 比較 | 結果 | 除外・限界 |
|---|---|---|
| 29ケースの予測・次週全state・店長実効案・出店見積り | 全件一致 | 数値や経済stateの除外なし。4地区3形態、満席/余力、品質85/100、店長通常/低満足維持、過剰人数、Lv2、2〜4店、自己所有、借入黒字/赤字、空会社を含む |
| 保存前後のenvelope | 本文・checksum・format・schemaが全件一致 | `savedAt`だけ除外。作成時刻は実行ごとに変わり、payloadのハッシュ対象でもない。経済値を隠す除外ではない |
| 保存の読戻し | 入力state・次週stateとも一致 | API担当の比較に加えて研究側で次週envelopeのdecodeも明示照合 |
| 新APIのresultと従来report | 各実店舗で一致、従来reportの5フィールドを維持 | 空会社の店舗単位比較は対象0店。不存在IDの挙動をこれだけで検証したとは数えない |
| 読み取りによるstate変更 | なし | 店長案や新説明を週次保存へ追加していない |

29ケースのうち旧engineとの照合を追加した研究担当の結果は `/workspace/shared/shibuya-artifacts/store-insight-economy-v042/independent-fixtures.json`。API担当の元記録は [store-insight-api-verification.json](../store-insight-api-verification.json)。生成時刻以外に比較対象を削除していないことを確認した。

加えて、既存の店舗戦略研究を新engineで再実行した。元スクリプトは出力先を指定するCLIがなく、既存JSONへ固定出力する。そのためリポジトリのスクリプトは変更せず、`/tmp`へコピーし、importの絶対パスと出力先だけを変更して実行した。旧研究のJSONとスクリプトは実行前後のSHAが一致しており、上書きしていない。

**2,178回の明示予測と373回の週決算を含む結果は、JSONの深い比較でもバイト単位でも完全一致した。除外フィールドは0。** 両方のSHA-256は `c1623ceaaadd21d9da0724e3083df6705e4432541a267ce644123a13e0a0baba`。実験仕様の`sourceVersion: 0.4.1`等もそのまま比較し、新実行のエンジン識別情報は別の結果ファイルへ保存した。仕様ラベルを新実行が旧engineだったという意味には使わない。

新実行の結果・基準不変の確認・旧/新engine SHAは `/workspace/shared/shibuya-artifacts/store-insight-economy-v042/result.json`、新実行の全データは同フォルダの `store-strategy-study-new-engine.json`。検査前後で新engineのSHAも不変だった。経済一致の対象はこの代表的な候補集合であり、すべての将来stateや別の機能の無変更を証明するものではない。

資本担当の[会計レビュー](store-insight-accounting-review.md)は、別の6状態を実行し、1円の丸め調整、自用物件の全社側費用、店長の配分枠と実費の区別を確認している。これは追加の計算・意味の証拠で、実ブラウザ操作や人間の理解とは分ける。DOM担当の検証が完了しても、それだけで初見ユーザーの改善判断や面白さが成立したとは報告しない。
