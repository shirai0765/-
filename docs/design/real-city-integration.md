# 実測渋谷と経営画面を接続する次の実装

2026-10-06、ソース・取得済みコンテナ・保存済みQA記録を読み取った設計案。今回の調査ではGPU描画、地形編集、候補地点の現地確認は行っていません。

最初の実装は、同じアプリ内で実測シーンへ切り替え、4地区の「ゲーム内の出店地点」をクリックして既存の出店・店舗管理を操作できるようにします。既存セーブの `lotId` を維持し、経営結果から実測シーン上の同じ目印へ戻れるところまでを一つの完了条件にします。現在の別ページを開く機能は、この統合には数えません。

現行変換順序は `localENU × ancestorTransforms × RTCTranslation × rotateX(π/2) × glTFVertex`。地理座標の点は同じWGS84楕円体からECEFへ変換し、同じENU行列を適用します。高度未確認の点に50mを入れた結果は水平位置の仮置きに限り、店舗の接地高さには使いません。精度テストには既存の[GLB再読込結果](../../../shared/shibuya-artifacts/real-shibuya-glb-qa.json)の境界差5cm未満を基準として再利用できます。

LOTSは単一の縮尺・回転で実測街へ整合するようには作られていません。例えば架空108の(-43,-34)と、実測ビューアの109周辺の注視点(-170,28,-4)は異なります。後者も建物を測定した設置原点ではありません。全LOTをアフィン変換して配置する案は採りません。

## 建物IDと4地点の調整開始位置

20末端b3dmをバイナリ読取した結果、batch数は1,013、`gml_id`も1,013件で重複なしでした。GLBの頂点属性には `_BATCHID` があり、batch tableには `gml_id`、`uro:BuildingIDAttribute_uro:buildingID`、名前、位置等があります。`_x/_y` はbinary DOUBLEで、読取値は経度・緯度に対応します。単なるJSON配列として読むと失敗します。`_zmin/_zmax`の標高基準は今回独立検証していないため、その数値をローカルYへ直接代入しません。

現在の `loadTile` はfeature tableとRTCを読みますが、batch tableをアプリの建物索引として保持しません。最小変更は、取得ファイルhashに結び付けた `{tileUri,batchId,gmlId}` 索引を追加し、復号後の頂点から各建物のローカル境界を一度だけ計算することです。クリック処理は復号後に残るカスタム属性名を実確認し、raycastした三角形のbatch値を検証してIDへ引きます。タイル全体を一つの建物として扱わないでください。

## 最初の完成範囲

1. `RealCityScene` を同App内の選択式画面にし、ゲーム街と実測街は片方だけマウントします。GameStateはAppの一つを共有します。見た目切替だけでは週・現金・設定を変えません。旧セーブへ位置を埋め込まず、lotId→表示アンカーを独立データとして引きます。
2. 4地点の目印を出し、未開店/営業中/ゲーム内物件保有を形と短い文字で区別します。「ゲーム内の出店地点」「ゲーム内で保有」と表記し、実ビル全体が売買対象に見える塗りつぶしを避けます。点のクリック→既存区画パネル→既存applyActionの順で処理し、描画側で現金や店舗配列を変更しません。
3. 出店結果の「店の様子を見る」を、選択中の地図の確認済みアンカーへ接続します。店名・営業形態・経営状態を同じlotIdから表示し、閉店で所有目印を更新します。戻る操作は実測街の全景へ戻し、経営対象を維持します。
4. 店の外観は段階を分けます。初回の4地点は目印と店名までを保証し、既存カフェGLBを見る操作は「架空店舗の外観プレビュー」と明示します。その後center-01の1地点だけ、実ファサードの幅・接地・歩道との関係を確認し、架空の入口/看板を重ねる実装を行います。8.14m幅の既存カフェGLBを建物中央へそのまま埋めたり、実ビルを全部置き換えたりしません。GLBが収まらない場合は寸法に合う小さい入口部材を作ります。これで初めて、その地点の「実測街の中に自分の店が見える」を達成したと扱います。

未配置の28区画は既存ゲーム街から引き続き操作できます。実測街の32地点が完成したような表示はせず、対応範囲を明示します。第一段階の合格条件は4地点で本物の経営操作が往復できることです。近景の写真らしさを保証する段階ではありません。

常時説明は「実測の街に、架空の経営を重ねています」。物件パネルには「出店地点・賃料・売買価格・人流はゲーム設定です。実際の募集物件ではありません」。出典と撮影時期の制約は残します。実在名称を目印として示すことと、架空事業を実在企業のものと表示することを分けます。

## 地面・近景・109の条件

[地表](../../src/realcity/Ground.ts)は72枚の写真を単一平面へ置き、位置Yは全建物の最小Y−0.2m、写真分のオフセットは+0.015mです。建物は元の高さを保持するため、坂道側で足元が浮きます。遠景の目印は建物上のラベル位置を使えますが、歩道レベルの店舗外観や歩行カメラには不十分です。DEMを追加する際は標高/楕円体高/ジオイドの基準を揃え、道路写真と建物の接地を一緒に検証します。坂を水平へ潰したり、各建物を地面まで下げたりして整合したと扱いません。起伏未解決の地点では地上近景を提供しない判断が必要です。

LOD2は屋根・外形と撮影済み画像が中心です。元のatlasを拡大しても窓・入口・細い看板の情報は増えません。地表は約0.5m/画素で、歩道の近景用素材でもありません。明るさ調整と詳細部材追加はできますが、建物全体の写真解像度を高めたと表現しません。入口の近景は個別に作った架空部材と出典モデルの境界が分かる設計にします。

[展示109](../../../shared/shibuya-artifacts/blender-polish/109/109.glb)は写真を参考にした推定再構築、48,785三角形・20メッシュ・18材質。実測原点は持たず、舗道原点・glTF Y-up・+Z正面です。ゲームのpublicモデルは別の架空108です。109を実測街へ載せるには、該当建物のgml IDを外形と写真で特定し、足元と正面方位を確認して `translate(localPosition) × rotateY(yaw) × modelLocal` を確定します。ビューアの注視点を設置位置に流用しません。

今回の末端batchの名前には109を同定できる文字列が見つからず、建物IDの確定は未実施です。置換時はそのIDに属する三角形だけを非表示にします。複数建物をまとめたメッシュ/タイルを丸ごと消すと隣棟も消えます。batch単位のインデックス分離をオフラインで行うか、表示用派生ジオメトリで一度だけフィルタし、元データと差分を保持します。109と元PLATEAUを同時に描いて重なりを隠す方法は採りません。置換表示には「109のみ推定再構築」と付記し、原データ表示へ戻せる構造にします。これは4地点の目印接続より後の作業です。

## 負荷の実数と実装予算

| 読取・保存記録から分かる値 | 数値と意味 |
| --- | --- |
| 20末端b3dm | 合計60,235,184 bytes、218,799三角形。今回コンテナを再集計 |
| 地表込みGLB | 65,737,364 bytes、218,943三角形、112メッシュ、92画像。[再読込QA](../../../shared/shibuya-artifacts/real-shibuya-glb-qa.json)の値 |
| 建物atlas | 20枚。RGBA8基底画像換算1,073,741,824 bytes＝1 GiB。今回画像寸法から計算。mipmapを含めれば概算4/3倍。実VRAM計測値ではない |
| 地表 | 72メッシュ、144三角形、通常72描画呼び出し。JPEG合計1,387,748 bytesとGPU上の展開量は別 |
| 既存の一視点記録 | [real-shibuya-qa.json](../../../shared/shibuya-artifacts/real-shibuya-qa.json)に37 calls / 200,249 triangles。視錐台・撮影時の地表構成に依存し、全シーン上限や現在のFPSを表す値ではない |

最初に効く対策は画像メモリです。元ファイルを保存したまま、統合版用の派生atlasを別出力し、低品質では最大1024²/枚（20枚がすべて正方形ならRGBA基底上限80MiB）、選択中の街区だけ2048²へ上げる構成を検討します。高解像度版を交換したら旧GPUテクスチャを解放します。縮小は近景を改善する対策ではなく、起動可能な負荷へ収める対策です。原画品質への切替は負荷と未検証端末の扱いを明示します。

建物20タイルを毎週再構築せず、static層・所有marker層・選択店舗層に分けます。経営更新は最大32目印のインスタンス色/状態と変更された店名だけへ反映。ポインター移動ではmarkerを先に判定し、必要な時だけ候補街区へraycastします。1,013建物の境界は復号時に一度計算し、毎フレームの全頂点走査を避けます。現行の要求時描画を維持し、常時動く群衆・車両は第一段階へ入れません。

提案する追加表示の予算は、marker形状・状態リング計4 draw calls以内、ラベルは選択地点中心、追加店舗外観は選択中の1件だけです。この数字は実装予算であり、実測結果ではありません。Dracoの既定worker上限2と直列decodeを出発点にし、4 CPUコアの環境で複数ビューアを並走させません。GLB一括読込や単一HTMLのbase64はネットワークサイズを減らせても、画像展開・文字列保持・decode中のCPU/RAMピークを解決しません。

合格測定は初回表示時間、選択地点の準備時間、JS heap、renderer.infoの描画数/三角形/texture数、シーン離脱後の解放、カメラ移動中のフレーム時間です。WindowsのGPU性能・FPSは現状未計測なので目標値を達成したと書きません。品質切替と往復を繰り返してメモリが単調増加しないことも確認します。

## 次の実装の受入確認

- 四つの参照建物について実描画で位置・方位・目印と隣棟の関係を確定。空室確認とは分ける。
- 既存セーブ→実測街→目印選択→出店→週次決算→同じlotIdの営業中目印まで同一GameStateで操作。
- 見る/戻る/地図切替だけの保存state一致。閉店・物件売却は既存actionの結果だけを反映。
- 原点・RTC・祖先transform・GLB再読込を検証し、二重変換やモデルの遠方飛びを防ぐ。
- 部分読込・404・Draco失敗でも既存ゲーム街と経営パネルへ戻れる。実測街が準備中なら操作可能に見える無反応markerを出さない。
- 390pxとdesktopで店名を読め、建物内部・地面下へカメラを入れず全景へ戻れる。1地点の外観接続を行う場合は入口と接地の実画像を残す。
- 元PLATEAU/写真のhash不変、派生画像/置換部分の明示、出典表示、上記負荷の測定値を納品記録へ残す。
