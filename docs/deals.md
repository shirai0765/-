# 営業提案 — 0.4.0

開業済みの会社へ12週単位で店舗向け提案を生成する。第1バッチ（第1〜12週）は在庫・発注支援と割高な広告の2件、以降は下記カタログを循環する。0.4.0で新たに生成する店舗カタログ提案は、作成時の事業状況を使うv3形式。保存済み提案は置き換えない。同じ種類の稼働契約は1件までで、提案の有効期限は作成週＋5週。

現金・直接保有不動産の取得額・既存子会社の取得額の合計が5,000万円以上になると、26週単位で不動産提案も加わる。不動産提案の初回は無印、以後はv2を維持する。営業提案の契約は上場の必須条件ではない。

## 契約前に比較するもの

営業担当の提示効果・提示利回りは費用控除前の事例で、成果保証ではない。初期費用、週額費用、契約期間、導入待ち、解約料、残価を契約前に表示する。調査前から保守的・楽観的な効果幅と、満了までの純収支幅を読める。

`満了までの純収支 = 効果 × (契約週 − 導入待ち) − 初期支払 − 週額費 × 契約週 − 支払済み調査費 ＋ 残価`

途中解約なしの試算。上限の効果でも回収が難しい場合は、その旨を表示し、調査せず見送ることもできる。調査後の画面の純収支には調査費を含めるが、再請求はしない。旧提案の保存済み調査文面は互換性のため維持する。

有料調査は類似事例・条件に基づく効果幅を絞るだけで、実現額は確定させない。初期支払・調査料・解約時の清算は操作時に現金へ反映。週額費用は契約した週から毎週の営業利益を減らす。効果は案件ごとの導入待ち後に決算へ入り、店舗向けは2〜6週、不動産は4〜6週の待機がある。初期費用と継続費用を同じ利益項目へ二重計上しない。

不動産案件は街区物件とは別の契約資産。520週の契約が終了する決算で残価を現金回収する。途中解約は残価から解約料を引いて清算。残価は固定のゲーム条件であり、実世界の売却価格保証ではない。稼働契約の残価を純資産に算入し、現金回収は営業利益に含めない。

## 作成時の店舗適性

新しい店舗カタログ提案では、その時点の店舗数と、直近決算に含まれる現存店舗の観測店舗数・客数合計・損益0以下の店舗数・決算週を固定する。閉店済み店舗の決算結果は除く。観測結果がなければ「未観測」と表示し、実績客数0とは区別する。

- POS・省エネ・人員支援は客数を稼働量の代理指標にする。共同仕入れは店舗数と客数、育成・顧問は店舗数を使う。
- 会員アプリは対象客数、法人仲介は既存客数が少ない場合の追加受注余地を代理指標にする。待ち行列・電力・再来店率・法人需要などを実測したとは扱わない。
- 客数要因は観測店舗あたり週1,000人、規模要因は5店舗で上限に達する。未観測なら客数要因で幅を縮めず、店舗数要因は引き続き適用する。損益0以下の店舗数は判断材料として表示し、赤字への利益ボーナスには使わない。
- 効果幅は元カタログの25〜100%内で、初期費用・週額費・期間は据置き。営業の最大事例の提示額は変えないため、自社状況を反映した幅と見比べられる。

作成済み提案の前提・効果幅・調査結果・実現額を、その後の出退店や設定変更で再計算しない。結果の不確実性はシードと案件キーから決定的に計算し、保存の再読込では再抽選しない。店舗向け契約は全店閉店中には効果を収益へ計上せず、週額費用は続く。

これらはゲーム内の代理指標と設計値であり、現実の企業開示から推定した収益率ではない。契約は店舗の価格・人員・評判を直接書き換えず、全社の週次効果と費用に計上する。実店舗ごとの行列や研修定着などのモデルは未実装。詳細は[店舗適性と保存形式](deals-context.md)を参照。

| 第2バッチ以降 | 日向：会員アプリ | 値引き控除後の効果、4週の定着待ち |
| 第2バッチ以降 | 森川：省エネ診断 | 低い利用料と32万円の設備投資 |
| 第2バッチ以降 | 黒瀬：経営顧問 | 65万円の着手金、5週の分析期間、高額固定費 |
| 3店舗以上または上場 | 藤沢：シフト・採用支援 | 追加人員費控除後の効果、39週契約 |
| 3店舗以上または上場 | 青葉：共同仕入れ | 廃棄・配送費控除後の改善、固定費 |
| 3店舗以上または上場 | 小坂：法人ケータリング | 追加食材・配送費控除後の成約効果 |
| 5店舗以上または上場 | 橘：店長育成・監査 | 80万円の初期費用、6週の研修、52週契約 |
| 資産5,000万円以上・不動産第2バッチ以降 | 水野：中古ワンルーム | 空室・修繕を織り込む効果、残価との差額 |
| 同上 | 榊：サブリース | 賃料見直し、高額初期費用、低い残価 |

解放後も各バッチの候補を循環し、全商品を同時に並べるわけではない。「週額費用控除前の効果」は別途利用料を引く前の意味で、追加原材料・配送費等は各商品の説明どおり効果から控除済み。

## 保存と決算の境界

無印v1・v2の既存提案は金額・文面・調査・実現額を維持する。新しい店舗カタログだけ `-v3-商品キー-固定前提` のIDを使い、保存スキーマ1のまま現在の店舗状況に依存せず再構築する。営業データ `deals` のない旧保存も読める。読み込み時は既知の商品・ID・前提値・作成週と、再構成した条件・実現額を照合する。元提案が残っている契約では両者の保存内容も比較する。詳しい制約は[保存契約](saves.md)を参照。

[getOffers / initializeDeals](../src/sim/deals.ts) は入力を変更せず提案を生成する。表示だけで未保存の新規提案を作る場合は、その時点の状態を使う。生成結果が状態へ保持された後は前提を固定する。`applyDealAction` が操作時の支出を処理し、`getDealFinancials(state, true)` が決算の効果・継続費用を返す。エンジンが現金増減へ一度だけ反映する。

`tickDeals` は同じ週の重複処理を防ぎ、実現値・累積費用・契約終了・仕入先株価を更新する。仕入先のゲーム株価への影響は契約初回決算だけで、初期費用の10%を時価総額で割った比率、上限0.05%。実世界の株価予測ではない。満了時の残価は `getDealMaturityCash` を決算の現金増減へ加える。

旧版84条件の互換性・v3固定前提・不正値拒否は[営業適性テスト](../tests/deals-context.test.ts)、実UIの調査・契約・決算・再読込は[DOMプレイテスト](sales-context-playtest.md)で確認している。
